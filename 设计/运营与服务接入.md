# 运营与服务接入

当前版本完成了运营后台、站内通知、举报申诉、短信账号验证、私有文件上传，以及支付退款和项目结项。短信与支付供应商尚未确定，接入层使用可配置的 HTTPS 网关合同；默认关闭外部短信和支付。所有业务 SQL、权限判断和事务仍在 C DBOP，Java 负责会话、参数校验、文件和网关适配。

## 1. 部署与数据库升级

新数据库使用 `设计/schema.sql`，它由版本迁移汇总生成，包含截至 `006_finance` 的结构。已有数据库先完成 `001`、`002` 的迁移及历史数据预检，再在备份完成、业务写入停止后依次执行：

| 顺序 | 文件 | 主要变化 |
| --- | --- | --- |
| 003 | `migrations/003_operations.sql` | 独立 `account_state`、会话版本、通知、管理员审计、举报事件与结项申请 |
| 004 | `migrations/004_account_security.sql` | `phone_verified`，既有账号默认未验证 |
| 005 | `migrations/005_files.sql` | 上传元数据、材料引用和按用途/提交版本控制访问 |
| 006 | `migrations/006_finance.sql` | 资金账户、支付/退款/支出订单、回调去重和不可覆盖的资金流水；累计金额扩大到 `DECIMAL(14,2)` |

这些迁移可重复执行，完成记录写入 `schema_migration`。迁移依赖 InnoDB、JSON、CHECK 和外键支持。不要并发执行迁移，不要在升级过程中恢复旧应用写入。升级后先确认 `003_operations` 至 `006_finance` 全部存在，再启动本版本 API 和 C 服务。既有账号密码保留，冻结状态不再覆盖原有业务审核状态。

SQL 迁移不会为旧余额补造支付订单或流水。旧项目即使已有 `current_donations_received`，也不能据此自动产生一笔“已付款”订单；详见资金核对部分。

Java 的常用基础配置如下，DBOP/IAM 仍按各自现有配置部署：

| 环境变量 | 默认值/含义 |
| --- | --- |
| `SERVER_PORT` | `8080`，Java API 端口 |
| `CROSSDO_DBOP_URL` | `http://127.0.0.1:1900` |
| `CROSSDO_IAM_URL` | `http://127.0.0.1:10089` |
| `CROSSDO_SERVICE_NAME` | `CROSSDO_WEB` |
| `CROSSDO_SERVICE_PASSWORD` | 无默认凭据，配置服务注册密码 |
| `SPRING_REDIS_HOST` / `SPRING_REDIS_PORT` / `SPRING_REDIS_PASSWORD` | `127.0.0.1` / `6379` / 空；保存登录会话、验证码摘要和限流状态 |
| `CROSSDO_SESSION_TTL` | `PT2H`，ISO-8601 时长 |
| `CROSSDO_UPLOAD_DIR` | `./var/uploads`，应改为持久绝对路径 |

## 2. 首位管理员离线引导

管理员不能通过网页注册。先通过正常短信验证注册一个由指定管理员实际控制的账号，记录其 UUID，再由拥有数据库运维权限的人员执行 `tools/bootstrap_admin.py`。脚本只接受已存在且 `phone_verified=1` 的 UUID，不创建账号、不设置密码，也不代替短信验证。

例如，先准备仅运维人员可读的客户端配置文件 `/etc/crossdo/admin-db.cnf`，使用 `[client]` 配置数据库连接、用户名、密码及所需 TLS 选项。连接账号需要读取目标用户、更新指定用户字段及插入 `admin_audit` 的权限，不需要创建数据库或存储过程权限。

先预览：

```bash
python3 tools/bootstrap_admin.py \
  --defaults-file /etc/crossdo/admin-db.cnf \
  --database crossdo \
  --user-id 11111111-1111-4111-8111-111111111111 \
  --note '运维人员姓名，授权工单编号，首次管理员引导'
```

核对输出中的目标 UUID、原角色和会话版本后，以相同参数增加 `--apply` 执行。也可使用 `--mysql-user`、`--mysql-host`/`--mysql-port` 或 `--mysql-socket` 指定连接，并通过 `--ask-password` 私密输入数据库密码，或设置 `CROSSDO_ADMIN_MYSQL_PASSWORD`；密码不放在命令行参数中。`--mysql-binary mariadb` 可切换客户端。

执行会在同一事务内将账号设为 `user_permission=1`、`user_status=0`、`real_name_authentication=1`、`account_state=active`，递增 `session_version` 并写一条 `bootstrap_admin` 审计。第一次引导时还没有管理员身份，审计的 `actor_id` 使用目标账号 UUID，`note` 同时记录数据库 `CURRENT_USER()` 与运维填写的授权理由。脚本输出审计 UUID，便于核对。

重复执行 `--apply` 会再次递增版本并新增审计，不属于无副作用重试。遇到超时或连接中断，先按错误提示的审计 UUID 查询是否已提交。审计写入失败时，尚未提交的授权会回滚。授权后用户须重新登录；既有会话失效。原账号若被冻结，执行也会恢复为 active，因此应使用专用管理员账号并核对原状态。

## 3. 六项功能的日常使用

| 功能 | 页面/接口 | 使用要点 |
| --- | --- | --- |
| 运营后台 | `/admin`，`/api/admin/*` | 审核志愿者、冻结/恢复账号、查看积压任务并转派；每次改变都填写理由 |
| 站内通知 | `/notifications`，`/api/notifications/*` | 审核、任务变更、举报处理、资金和结项事件产生通知；仅接收人可读取和标记已读 |
| 举报申诉 | `/cases`，`/api/cases` | 举报指定一个项目或账号；案件参与人可对已处理案件提出关联申诉 |
| 短信账号安全 | 注册、找回密码、账号换绑页 | 验证码绑定手机号、用途及换绑用户；密码重置/换绑撤销旧会话 |
| 文件材料 | 申请、项目、举报和支出材料上传 | PNG/JPEG/PDF；私有材料需登录读取，公开范围由已提交版本和用途决定 |
| 支付退款与结项 | `/donations`、项目页、运营资金/结项页 | 订单、退款、支出有明确状态；到账由已验证回调或开发模拟确认；资金结清后方可结项 |

运营权限要求账号为 active、角色 1、审核状态 0、实名认证通过。志愿者认证仅针对角色 5/7，批准后状态变为 0；驳回为 5。冻结只改变 `account_state` 并撤销会话，保留原审核进度；页面不允许冻结管理员或自己。

任务转派仅适用于已接单审核状态 3/7。新的审核员须是有效、已认证志愿者，且不能审核自己的申请；选“释放”则回到待接单状态 2/6。页面会提示超过 24 小时的任务，系统保留转派理由和历史负责人，不会自动转派。

举报本身不会自动冻结账号。运营人员核实后选择 `resolved` 或 `dismissed` 并写明依据；确需冻结时另走账号管理。材料上传用途选择 `case`，其文件仅上传人和管理员可读；被举报人或项目方可以看案件及处理记录，但响应不含他人提交的证据链接。案件参与人可以申诉，同一参与人不能对同一父案件同时创建多条未处理申诉。

通知是站内消息，不会自动发送短信、邮件或第三方聊天消息。短信适配器仅承担明确请求的账号验证码。

## 4. 上传文件的持久存储和访问

生产部署显式设置如 `CROSSDO_UPLOAD_DIR=/var/lib/crossdo/uploads`，挂载持久卷，确保 Java 运行用户可读写，并将目录与数据库元数据一并备份。目录不能放在前端 `public`、Web 静态目录或容器临时层。Linux 上服务尝试将目录设为 0700、文件设为 0600。

文件使用服务器生成的 UUID 命名，流式计算 SHA-256，以实际内容特征识别 PNG/JPEG/PDF，不接受 HTML/SVG。单个文件限 10 MiB，每账号累计元数据对应内容限 500 MiB。`POST /api/files` 接受 multipart 字段 `file`、`purpose=application|project|case`，其中 project 还需 `project_id`。返回的 `/api/files/{uuid}` 是受控下载地址，不是磁盘路径。

上传完成并不表示公开。申请材料仅所有者、管理员和当前指派审核员可读；项目材料只有被已批准或已结项项目当前提交版本正式引用后才可公开，旧版本仍按私有材料授权。案件材料始终按 owner/admin 授权。支出凭证在付款确认成功后按项目公开范围展示。私有下载使用请求头 Bearer 会话，不将令牌放进 URL。

多 Java 实例需共享同一持久文件卷；当前本地存储实现没有对象存储同步功能。数据库写入结果不确定时文件会保留，避免已提交引用失去内容；清理疑似孤立对象前须核对 `uploaded_file` 与 `file_usage`，不能仅凭一次请求超时删文件。

## 5. 开发模式和生产配置

| 配置 | 默认值 | 可选值/用途 |
| --- | --- | --- |
| `CROSSDO_SMS_MODE` | `disabled` | `disabled` / `development` / `gateway` |
| `CROSSDO_SMS_GATEWAY_URL` | 空 | 短信适配器的完整 HTTPS POST 地址 |
| `CROSSDO_SMS_GATEWAY_KEY` | 空 | 短信网关 Bearer 密钥 |
| `CROSSDO_PAYMENT_MODE` | `disabled` | `disabled` / `development` / `gateway` |
| `CROSSDO_PAYMENT_GATEWAY_URL` | 空 | 支付网关 HTTPS 基地址，不含查询参数/fragment |
| `CROSSDO_PAYMENT_GATEWAY_KEY` | 空 | 支付网关 Bearer 密钥 |
| `CROSSDO_PAYMENT_WEBHOOK_SECRET` | 空 | 支付回调 HMAC 密钥，至少 32 个字符 |

支付配置还支持 Spring 属性 `crossdo.payment.mode`、`crossdo.payment.gateway-url`、`crossdo.payment.gateway-key`、`crossdo.payment.webhook-secret`；上传支持 `crossdo.upload.directory`。显式 Spring 属性优先于对应环境变量回退值。短信服务直接读取表中 `CROSSDO_SMS_*` 配置。

本地集成测试可显式设置两个 MODE 为 `development`。该模式中，短信验证码以 `development_code` 返回给当前请求，支付、退款和支出使用清楚标示的模拟确认接口；没有真实短信发送、收款或出款。开发验证码不会写入普通日志，Redis 保存验证码摘要而非明文。

生产必须使用 `disabled` 或已完整配置的 `gateway`。不要向公网部署 `development`：当前实现依据 MODE 判断，单独设置 `SPRING_PROFILES_ACTIVE=prod` 并不会覆盖错误设置的 MODE。没有供应商时保持 disabled；验证码发送和新资金操作会提示服务未配置，不会跳过验证码，也不会自动改成模拟模式。禁用支付时不应遗留等待实际回调的真实订单，应先完成在途结算或保留可接收回调的 gateway 服务。

开发账和真实账不能在同一项目混用。资金账户和订单记录绑定创建时的 mode，切换服务模式不会迁移或抹除既有账目；真实接入验收使用独立环境、数据库和项目。

## 6. 短信网关合同

Java 向 `CROSSDO_SMS_GATEWAY_URL` 发出 HTTPS POST，头部为 `Authorization: Bearer <key>` 和 `Content-Type: application/json`。请求示例：

```json
{
  "phone_number": "13800000000",
  "purpose": "register",
  "code": "123456",
  "expires_in": 300,
  "idempotency_key": "11111111-1111-4111-8111-111111111111"
}
```

`purpose` 为 `register`、`password_reset` 或 `phone_change`。网关将该合同适配为供应商签名、模板和发送接口，2xx 表示接受发送，响应体不使用。请求连接超时 5 秒，总请求超时 8 秒，不跟随重定向；失败不会保留可消费的挑战记录，调用方得到服务不可用提示。

验证码有效期 300 秒，最多 5 次错误尝试且仅能成功消费一次；同手机号同用途发送间隔 60 秒。Redis 进一步限制每手机号每小时 30 次、每来源地址每小时 60 次。来源地址取 Servlet 连接信息，不直接信任客户端提交的 `X-Forwarded-For`；反向代理需要正确配置可信转发地址处理，避免所有用户共用代理地址额度。

换绑还验证当前密码，验证码绑定已登录用户。旧账号升级时 `phone_verified=0`，不会被脚本自动改为已验证；应完成正常手机号验证流程后才能作为管理员引导目标。

## 7. 支付网关和回调合同

Java 在数据库提交订单/预留资金后调用网关，不在数据库事务内等待网络。网关基地址下约定三个 HTTPS POST：

| 路径 | 必需请求字段 |
| --- | --- |
| `/payments` | `reference_id`、`idempotency_key`、`amount`、`currency`、`project_id` |
| `/refunds` | 上述字段加 `payment_reference_id` |
| `/disbursements` | 上述字段加 `payout_reference` |

`reference_id` 为平台支付/退款/支出记录 UUID；发往网关的 `idempotency_key` 和 `Idempotency-Key` 请求头均使用该记录 UUID。该值与前端创建操作传入、按用户约束唯一的幂等 UUID 分工不同：前端幂等值避免重复创建平台记录，记录 UUID 避免重试时重复产生供应商交易。相同幂等值不能用于不同金额或不同业务目标。

金额以十进制字符串传输，例如 `"25.00"`；币种固定 `CNY`，禁止以浮点换算金额。API 单笔金额最多八位整数和两位小数，累计账面金额使用 `DECIMAL(14,2)`。网关需将金额、收款目标及平台引用完整映射到实际供应商接口。`payout_reference` 是运营配置的收款引用，不能作为公共项目内容返回。

请求头包含 Bearer 密钥、JSON Content-Type 和 Idempotency-Key；连接超时 3 秒、请求超时 8 秒，不跟随重定向。2xx 响应必须为 JSON 对象，支付创建须返回完整 HTTPS `checkout_url`，如：

```json
{"checkout_url":"https://payments.example.com/checkout/provider-reference"}
```

网关受理响应不会直接认定资金到账，真实成功/失败仍由签名回调确认。超时、服务错误或不完整响应会保留平台订单与已预留资金，不能据此当作失败并重新发起另一笔款项。支付可通过 `POST /api/donations/{id}/checkout` 重试；退款通过 `POST /api/refunds/{id}/retry`；已批准支出可再次执行批准动作重发同一记录。重试必须沿用记录 UUID，供应商适配器须支持幂等处理。

回调入口为 `POST /api/payments/callback`。请求体字段均为字符串：

```json
{
  "event_id": "provider-event-0001",
  "type": "payment",
  "reference_id": "11111111-1111-4111-8111-111111111111",
  "status": "succeeded",
  "amount": "25.00",
  "currency": "CNY"
}
```

`type` 为 `payment|refund|disbursement`，`status` 为 `succeeded|failed`。`event_id` 为 1–128 位字母、数字或 `._:-`，应稳定标识同一供应商通知。请求体限 64 KiB。头部：

- `X-Crossdo-Timestamp`：Unix 秒数，允许服务当前 UTC 时间前后 300 秒。
- `X-Crossdo-Signature`：`HMAC-SHA256(secret, timestamp + "." + 原始JSON请求体)` 的 64 位十六进制值。

签名覆盖 UTF-8 原始请求体，不能在签名后改变空格、换行或字段序列。平台用固定时间比较签名，核对币种、金额、记录模式和引用后，在同一事务中处理回调事件、订单终态、预留余额、项目累计金额和资金流水。重复相同 event 与相同原始载荷不重复记账；相同 event_id 但载荷不同返回冲突。资金记录进入终态后不会被另一次回调反转，需对网关终态语义保持一致。

网关供应商的真实凭据、模板和回调地址由部署者配置；仓库没有内置某家供应商账号或默认签名密钥。

## 8. 退款、支出、结项与日常对账

捐款仅对审核通过状态 0 的项目开放，不允许项目所有者给自己捐款。付款成功入账为正流水；退款和成功支出为负流水。退款申请先预留金额，管理员批准支出前也会保留申请金额，成功或失败回调分别扣减或释放，避免同时退款/支出导致透支。

项目所有者或管理员可提交结项原因及 `remaining_plan=refund|fully_used`。项目转为状态 12 后停止接收新捐款，但已有支付、退款和支出仍须完成。管理员批准结项需要同时满足：

- 没有 pending 支付、pending/processing 退款及 requested/approved/processing 支出。
- 资金账户 `balance=0` 且 `reserved=0`。
- 该项目 `fund_ledger.amount` 合计为 0。
- `current_donations_received - current_used_donations - 成功退款合计 = 0`。

通过后项目状态为 13，保留历史并清除所有者当前项目指针；驳回恢复为 0。选定 refund/fully_used 只是处理计划，不会自动发起退款、强行清账或绕过上述检查。只有实际全部结清后才能结项。目前新的支出申请要求项目仍为 0，因此选择 fully_used 时先完成所需支出申请，再提交结项；若结项中还需新增支出，由管理员驳回恢复 0 后申请。状态 12 可以继续完成既有支出和退款。结项结果可匿名读取，待审结项仅 owner/admin 可见，公开视图不含内部审核人和审核意见；发送了无效 Bearer 令牌仍会被拒绝。

运营人员每天在资金核对页或 `GET /api/admin/finance/reconciliation?limit=100&offset=0` 检查分页结果，比较 `balance`、`ledger_balance`、`cache_balance` 与 `matches`，同时排查长期 pending 的订单和占用的 reserved。累计 `received` 是成功收款总额，不因退款扣减；`refunded` 单独累计成功退款，`used` 是成功支出；用户累计捐助额按退款后净额计。

核对异常时，应对照供应商账单、平台订单、回调事件和审计记录定位差异，保留原始证据。当前核对接口只报告差异，不自动修复。迁移前遗留缓存金额而无真实订单/流水的项目会显示不一致，也会被结项校验阻止；没有提供“一键补账”功能，不能仅修改缓存值、插入伪付款或跳过余额检查来消除异常。应按真实原始账单完成经授权的专项数据迁移和复核，再恢复资金操作。

外部服务不确定结果先查已有记录，并使用原引用重试；不要删除流水或重建订单来解决重复回调。数据库和上传持久卷的备份、网关密钥轮换及日常监控由部署环境承担。

MariaDB 开启 `innodb_snapshot_isolation` 时，在旧快照建立后读取并发更新的记录可能返回数据库错误 1020。服务将它与死锁/锁等待冲突一并映射为 HTTP 409，事务不会继续按旧余额批准结项。重新读取状态后，可使用原创建幂等键、原订单引用或原回调事件重试；不要为重试生成新的付款或退款幂等键。普通审核请求则按最新待审状态重新提交。409 也可能表示未结清或参数冲突，须先根据响应和当前状态区分原因。

可复现的资金读取并发回归位于 `tools/tests/closure_concurrency.py`：加载隔离测试栈环境后运行 `python3 tools/tests/closure_concurrency.py`。它建立随机临时数据库，直接提取生产 `wo_closure_settled` 的 SQL 并以 prepared statements 验证旧快照下五项校验仍看到最新已提交记录，完成后自动删除临时库。这是 SQL 层回归，不替代完整 API 流程测试。为验证 MySQL/InnoDB 的当前读行为，MariaDB 上仅测试读取连接设置 `innodb_snapshot_isolation=OFF`，全局变量和应用连接均不改变。
