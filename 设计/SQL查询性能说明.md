# SQL 查询性能说明

2026-11-06 对当前 DBOP 查询进行 MySQL 8.0.46 实测，并落实查询改写和前端摘要模式。常用查询在本次十万级合成数据场景中表现良好；线上容量仍需结合实际数据分布、网络和并发观测。

## 测试方法与结果

每张主要表有 100,000 条合成患者、申请、项目记录，另有两个合成审核人；99% 已完成审核，剩余包含待领取和不同审核人的已领取任务。每五条记录共享时间戳，以验证 ID 次序在同时间记录中的作用。病情初始每项目一条约 1 KB JSON。所有数据在独立临时测试库中生成。测试环境有效 CPU 配额为 4 核、内存上限 16 GiB，MySQL InnoDB 缓冲池为 384 MiB；按单连接串行测量。

每条查询先预热一次，再执行三次 `EXPLAIN ANALYZE`，取服务器执行时间中位数。表内时间不含客户端启动、HTTP、业务 JSON 组装或网络传输，也不是并发压测的延迟或吞吐承诺。

| 查询场景（每页 20 条） | 优化前 | 优化后 |
| --- | ---: | ---: |
| 患者申请任务首页 | 3.79 ms | 1.28 ms |
| 项目审核任务首页 | 2.57 ms | 0.420 ms |
| 公开项目主查询，跳过 10,000 条 | 16.9 ms | 2.93 ms |
| 公开项目病情关联，跳过 10,000 条 | 15.9 ms | 2.62 ms |

这些数值来自同一轮最终源码测量，硬件、缓存、数据分布和执行计划变化都会影响结果。测试没有把耗时阈值写成通过条件。

在 `offset=0/17/200/10000` 比较原 SQL 与优化 SQL 的完整结果及顺序，加上摘要和长历史检查，共 21 次校验通过。任务队列只有 526 个符合当前审核人条件的记录，所以任务队列 offset 10000 用于验证空页；性能表中的深分页数据来自具有 99,000 个公开项目的查询。

## 已落实的优化

1. **任务队列拆分查询条件。** 患者申请分为待领取与本人已领取两组；项目按四个互斥状态分支查询。每分支取最多 `limit + offset` 条，再按原时间及 ID 次序统一分页。避免一个 OR 查询把其他审核人的大量任务带进候选集，保持权限和分页结果一致。患者列表最终仅对本页记录读取完整展示字段。
2. **公开列表先分页 ID。** 先通过现有状态/时间覆盖索引找到本页 ID，再按主键取字段。跳过 10,000 条时仍需遍历 10,020 个索引条目，但只有本页 20 个项目需要回表读取。
3. **卡片使用有界摘要。** `GET /api/projects?summary=true` 每项目只读取当前版本第一条病情中的最多 240 字，返回 `summary` 而不返回 `pathography`。首页和项目广场已使用该模式。广场当前页搜索匹配昵称和摘要；详情及默认完整列表接口保持原数据范围。
4. **当前版本精确关联。** 完整列表先定位项目和 `submission_no`，再按 `(project_id, submission_no)` 索引查病情。用明确的联表次序避免只按项目 ID 读取所有旧版本再过滤。
5. **减少无用字段读取。** 用户查询不再读取密码、身份证号及 OpenID；项目与申请查询不再加载已停用的历史 TEXT 列。凭据读取仍走专门的手机号唯一索引查询。

这次直接使用已有索引，没有新增索引或迁移脚本。

## 病情历史增长的影响

另一个场景为首页 20 个项目各有 500 条当前病情，并保留两个旧版本。完整模式需要返回 10,000 条当前病情；优化后的完整查询约 33.7 ms，原查询约 31.1 ms，本轮没有改善这部分全量输出成本。

卡片摘要模式只返回 20 条，约 0.412 ms。该测试中 SQL 文本结果从 11,029,999 字节减少为 7,159 字节；这是 SQL 返回的 UTF-8 文本大小，不是 HTTP 压缩后的响应大小。摘要模式与完整模式的数据范围不同，完整资料仍可在详情查看。

## 复现与下一步

在专用 MySQL 8 测试实例执行以下脚本。需要 `EXPLAIN ANALYZE`（MySQL 8.0.18+）及建库、删库和建存储过程权限。连接设置支持与集成测试相同的 `CROSSDO_TEST_MYSQL_*` 环境变量；不要连接现有 MariaDB 测试栈运行此 MySQL 执行计划脚本。

```sh
python3 tools/tests/query_benchmark.py \
  --mysql-binary mysql --mysql-host 127.0.0.1 --mysql-port 3306 --mysql-socket='' \
  --rows 100000 --history-entries 500 --repeats 3 \
  --output /tmp/crossdo-query-report.json
```

脚本直接从当前 C 源码提取优化 SQL，以免测量与实现脱节；原查询保留为对照。脚本仅操作自身成功创建的随机临时库，结束时自动清理。JSON 报告包含执行计划、SQL、实际读取行数、三次时间及结果等价检查数。

本轮另通过 35 项 Java 测试、11 组真实业务回归、5 项浏览器回归和前端构建。既有接口默认行为、审核权限、完整详情和提交历史均保留。

后续按实际规模优先考虑：

- **游标分页**：深层 OFFSET 仍需要线性跳过索引条目；连续向后浏览量增大时，可使用时间与 ID 作为游标。
- **详情历史分页**：详情目前保持完整数组合同，病情和审核历史非常长时需要分页读取。这次摘要解决了列表增长问题，详情全量读取仍随历史数量增长。
- **申请状态独立存储**：申请待领取分支仍需跨用户表筛选、按申请提交时间排序。若同时待审的申请达到很大规模，可结合账号状态与审核状态分离，建立同表的状态/提交时间索引。
- **线上观测**：以慢查询日志、实际扫描行数、接口延迟和并发压测为依据继续调整；本次数据不代表生产峰值容量。
